### A.1 Create the Azure SQL server (5 min)

Microsoft Entra-only authentication, with **you** as the administrator – no SQL passwords anywhere:

```powershell
$me = az ad signed-in-user show --query "{id:id, upn:userPrincipalName}" -o json | ConvertFrom-Json
az sql server create -g $rg -n $sqlServer -l $location --enable-ad-only-auth `
    --external-admin-principal-type User --external-admin-name $me.upn --external-admin-sid $me.id -o none
# Let the on-premises server (data migration) and Azure services (the apps) connect:
az sql server firewall-rule create -g $rg -s $sqlServer -n onprem-server --start-ip-address $vmIp --end-ip-address $vmIp -o none
az sql server firewall-rule create -g $rg -s $sqlServer -n azure-services --start-ip-address 0.0.0.0 --end-ip-address 0.0.0.0 -o none
"$sqlServer.database.windows.net"                  # note this name for the next step
```

### A.2 Migrate the data – the DBA step (15 min)

Moving data isn't a code change, so it isn't Copilot's job: in real projects a DBA runs it, typically with the Azure Database Migration Service or SqlPackage. The lab includes a script that does it with SqlPackage, from the on-premises server.

1. On **your workstation**, create a short-lived access token for Azure SQL and copy it:

   ```powershell
   az account get-access-token --resource https://database.windows.net/ --query accessToken -o tsv | Set-Clipboard
   ```

2. **RDP** to the lab VM, open **Windows PowerShell as Administrator** and run it with **your** server name (paste the token when asked – the input is hidden):

   ```powershell
   powershell -ExecutionPolicy Bypass -File C:\ContosoSetup\src\scripts\Copy-DatabasesToAzureSql.ps1 -TargetServer sql-finance-0720c-team1.database.windows.net
   ```

   The script downloads SqlPackage (and checks its Microsoft signature), copies the schema and all data of `ThurayaFinance` and `ThurayaTreasury`, continues the number sequences, and compares every table's row count. Windows logins and the SQL password are deliberately **not** migrated.

   Expected (validation run):

   ```
   === ThurayaFinance   ... verified: 19 tables, 1,902 rows identical in Azure SQL
   === ThurayaTreasury  ... verified: 7 tables, 279 rows identical in Azure SQL
   MIGRATION_OK
   ```

   Row counts grow if people used the portal before the migration – what matters is that both sides match.

#### Give the apps access to their databases

Managed identities need a user in each database. Run this as yourself (the Entra admin), for example in the Azure portal: **SQL database → Query editor** (sign in with Microsoft Entra). Use the identity each app actually runs with – the migrated code decides (the treasury service, for example, reads `AZURE_MANAGED_IDENTITY_CLIENT_ID`, which points to a *user-assigned* identity):

- system-assigned: name = the app name, object ID = `az webapp identity show -g $rg -n app-portal-0720c-$team --query principalId -o tsv` (treasury: `app-treasury-0720c-$team`)
- user-assigned: name and object ID from `az identity list -g $rg --query "[].{name:name, principalId:principalId}" -o table`

In **ThurayaFinance**:

```sql
CREATE USER [<portal identity name>] FROM EXTERNAL PROVIDER WITH OBJECT_ID = '<portal identity principalId>';
ALTER ROLE db_datareader ADD MEMBER [<portal identity name>];
ALTER ROLE db_datawriter ADD MEMBER [<portal identity name>];
GRANT UPDATE ON OBJECT::dbo.budget_transfer_seq TO [<portal identity name>];  -- budget transfer numbers (NEXT VALUE FOR)
```

In **ThurayaTreasury**:

```sql
CREATE USER [<treasury identity name>] FROM EXTERNAL PROVIDER WITH OBJECT_ID = '<treasury identity principalId>';
ALTER ROLE db_datareader ADD MEMBER [<treasury identity name>];
ALTER ROLE db_datawriter ADD MEMBER [<treasury identity name>];
```

If the agent already created the users, these statements report that the user exists – that's fine. Restart both apps afterwards:

```powershell
az webapp restart -g $rg -n app-portal-0720c-$team
az webapp restart -g $rg -n app-treasury-0720c-$team
```
