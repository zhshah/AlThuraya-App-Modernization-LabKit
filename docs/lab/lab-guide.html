Hands-on lab · GitHub Copilot modernization

Move a legacy .NET Framework and Java application to Azure – with GitHub Copilot doing the work

Assess the code, get the customer's go-ahead, and let GitHub Copilot modernization do the rest end to end: modernize both applications, create the Azure resources and deploy the apps. Then prove they still work. One guide, one path, step by step.

How this guide works

WhoDoes
PresenterPart 1 once, before the event. Part 7 on the day.
EveryoneParts 2 to 6, in order – participants, and the presenter when rehearsing.
  • Every step tells you what to do and what you should see. When it matches, tick Done.
  • All addresses and names are already in the commands. Click Copy, paste, run. Only your team name can change – see Your lab at a glance.
  • In VS Code you use the modernization panel once, to start (3.3). After that everything happens in one Copilot Chat – see Where you work in VS Code.
  • Copilot does the work. Don't change the code yourself. Read what Copilot shows you, then approve.

The scenario

Al Thuraya Holding (fictitious) runs its Group Finance Portal on one Windows server in its own data centre: an ASP.NET MVC 5 portal on .NET Framework 4.8 in IIS, a Java 8 / Spring Boot 2.7 treasury service in Tomcat, and two SQL Server databases. The CFO wants it on Azure – without a rewrite project.

Build the lab (first time only)

35–50 min

Your lab already exists – skip this step. Run it only if the lab was removed and you need to build it again:

./onprem-vm/Deploy-Lab.ps1 -ResourceGroup rg-contoso-onprem-swc -VnetResourceGroup sweden-central-vnet -VnetName Sweden-vNet -SubnetName default
What it does

Creates the VM in your existing network Sweden-vNet (open only to your internet address), installs IIS, SQL Server Express, Java 8 and Tomcat, builds and deploys both applications with demo data, and tests everything. It reuses the same names, so the addresses in this guide stay valid.

It stopped with an error? Run the same command again – it continues where it stopped.

At the end it prints the portal, treasury and Remote Desktop addresses – the same as in Your lab at a glance.

What it does

AppCAT, the analysis engine, scans the code for everything that blocks a move to Azure: old runtimes, resources on the local server, passwords. This standard assessment fills the report's Issues tab – what the plan needs.

The Assessment Report tab (Report_ plus date and time), a summary of the findings in the chat, and Copilot's question – still unanswered.

3.4

Read the report

10 min
Do – in the Assessment Report tab
  1. Target Service shows Azure Kubernetes Service (AKS). Change it to Azure App Service – our target. The list then shows only what matters for App Service.
  2. On the Issues tab, start with the Mandatory findings – they block the move. Click › next to a finding to see the file, the line and the suggested fix.
  3. Don't click Create Plan – you plan in the chat in Part 4, after the customer's decision.

For Azure App Service, 3 findings – all in the treasury service (our test, effort S):

  • Local JDBC Calls – Mandatory: the service connects to a SQL Server on the same machine.
  • Password found in configuration file – Potential: the database password in application.properties.
  • Microsoft SQL database found – Potential: the database moves too.

With AKS selected you see 4 (plus No Dockerfile found), with Container Apps 5. Numbers can change with newer tool versions.

Only the treasury service in the report? That's how it ran in our test: for a repository with Java and .NET code, the assessment analyses the Java service. Copilot reads the portal's .NET code itself when it writes the plans (4.2), and every portal blocker – Windows authentication, Event Log, e-mail folder, local paths – becomes a task. The portal's findings from a separate .NET assessment are under All findings below.

Why are Architecture, API Contracts, Configuration, Business Workflows, Dependencies and Data Model empty? The standard assessment is Issue only: it fills the Issues tab. The six other tabs are 6 AI deep-analysis documents – architecture, dependencies, API contracts, data model, configuration and business workflows. Only a Custom Assessment with Full analysis generates them, and that takes much longer – 30 minutes and more. The plan doesn't need them: the standard assessment does the job.

Where is the report saved? In .github/modernize/assessment/ – one folder reports/report-<date and time> per report. Open it again any time from the Assessment Reports tab. Details: What Copilot writes where.

Optional – the full assessment (Custom Assessment)

Not needed for the lab. Use it to get the six extra tabs and a security scan – for example to prepare a customer demo the day before.

  1. Open the Assessment Reports tab (next to Assessment Report – it says Assess your app for modernization) and click Custom Assessment.
  2. Choose Assessment Domains: Java Upgrade, Cloud Readiness and Security. Analysis Coverage: Full analysis. Target Runtime: OpenJDK 21. Target Compute Services: Azure App Service. Target Operating System: Linux.
  3. Click Run Assessment. Copilot opens extra chats for the security scan and the six documents, for example Run security assessment plan. Let them work, and do the lab steps in the Migrate application to Azure chat.

In our test it added Java Version Has Reached the End of Support and 8 security findings (CWE, for example the hard-coded database password): 14 issues, effort L. The six documents hadn't arrived after more than 30 minutes and the report stayed at 99%. If that happens, click Stop Running – the findings stay in the report.

Security findings are only reported here. Copilot fixes them only if your plan request asks for it – see the two scopes in 4.2.
